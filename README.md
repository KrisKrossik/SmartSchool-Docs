## 1. Паспорт и идея проекта

### Название проекта
**«CodeHogwarts» (HOG Platform)** — интерактивная геймифицированная веб-платформа для обучения программированию.

### Идея и концепция проекта
Проект направлен на решение проблемы высокого порога входа и низкой вовлеченности при самостоятельном обучении IT-дисциплинам. В основе приложения лежит концепция **«Обучение через игру» (Edutainment)** в стилистике школы магии.

* **Целевая аудитория:** Подростки и молодые люди в возрасте 14+ лет, начинающие изучать программирование.
* **Ключевой функционал:**
  * **Адаптивный онбординг без стресса:** Система предварительно уточняет опыт пользователя. Для полных новичков обучение начинается с наглядных бытовых примеров (яблоки, логические цепочки) и «Модуля 0» (`print`, ввод/вывод), исключая испуг от сложного синтаксиса.
  * **Простая регистрация (14+):** Быстрый вход без необходимости подтверждения через родителей. На главном экране размещены Пользовательское соглашение и Политика конфиденциальности.
  * **Пошаговые интерактивные уроки:** Решение практических задач и написание кода на Python с мгновенной проверкой в Sandbox-среде.
  * **ИИ-ассистент:** Помощник на базе нейросети, который анализирует ошибки и дает понятные наводящие подсказки. В случае сбоя API автоматически срабатывает fallback на проверенные шаблоны.
  * **Геймификация и экономика:** Начисление монет, поддержка серии дней («Огонёк»), Колесо фортуны, мемы и коллекция из 54 ежей: скины покупаются за монеты, новые уровни коллекции открываются по модулям.
  * **Логирование и надежность:** Автоматическая фиксация сбоев в логах сервера с понятными уведомлениями для пользователя в интерфейсе при возникновении ошибок.
  * **Панель администратора (CMS):** Управление контентом, сброс прогресса, аналитика воронки и экономика.

### 4.4. Ресурсы проекта

Для реализации проекта используются следующие типы ресурсов:
* **Человеческие ресурсы:** Команда из 5 человек (PM/BA/Database Dev, Lead BA/Lead Designer, Team Lead/SA/Frontend Dev, Lead SA, Backend Dev/DevOps).
* **Инфраструктура и Хостинг:**
  * Сервер для деплоя бэкенда и Swagger UI (`https://maks.my/codehog`).
  * SSL-сертификаты для безопасности HTTP-запросов.
* **Инструменты разработки и сервисы:**
  * **Backend:** Python 3.14, FastAPI, SQLAlchemy 2.0 (ORM), Jinja2 (шаблоны).
  
  * **Database:** SQLite. Весь доступ идёт через ORM, поэтому переход на PostgreSQL меняет одну строку подключения.
  
  * **Frontend:** HTML5, CSS3, ванильный JavaScript — без фреймворка и без шага сборки.
  
  * **Безопасность:** bcrypt для паролей, itsdangerous для подписи сессий.

  * **Исполнение кода учеников:** отдельный процесс с лимитами по времени, памяти и объёму вывода.

  * **APIs:** Внешняя нейросетевая модель для генерации уроков и подсказок (OpenAI-совместимый интерфейс, модель deepseek-v4-flash).
  * **Логирование:** Стандартный модуль `logging` Python для фиксации ошибок и работы сервисов.
  * **Развёртывание:** systemd и nginx на собственном сервере.

Управление и Документация: GitHub (контроль версий и GitFlow), YouGile (Kanban-доска), Figma (дизайн и макеты).

### 4.5. Риски и способы их устранения

| Категория риска | Описание потенциального риска | План предотвращения и ликвидации (План Б) |
| :--- | :--- | :--- |
| **Технический** | Внешняя ИИ-модель недоступна или отвечает слишком долго (задержка > 3 секунд). | В бэкенде реализован механизм заглушек (Fallback): если ИИ не отвечает, эндпоинт `/hog/task/{task_id}/hint` отдает заранее заготовленную статичную подсказку из БД. |
| **Интеграционный** | Рассинхрон между разработчиком фронтенда/бэкенда и аналитиками по структуре JSON-ответов. | Строгое следование контрактам OpenAPI (Swagger). Любые изменения в API вносятся сначала в `API_Contracts.md`, согласовываются Леной (TL) и только потом пишутся в коде. |
| **Сбои UI / Баги** | На клиенте произошел сбой (например, не крутится Колесо фортуны). | Сервер пишет полный stack trace ошибки в логи, а пользователю выводится понятное модальное окно с кнопкой «Повторить попытку». |
| **Инфраструктурный** | Проблемы с доступом к серверу или домену `maks.my` прямо во время защиты работы. | Заранее подготавливается локальная сборка проекта, разворачиваемая одной кнопкой на ноутбуке, а также записывается видеодемонстрация (скринкаст) прохождения всех сценариев. |
| **Организационный** | Нехватка времени или болезнь одного из участников команды перед сдачей. | Кристина (PM) перераспределяет задачи в YouGile; критичные задачи (критический путь) перехватывают смежные роли (например, SA помогает с версткой/тестированием). |

### 4.6. Механизмы контроля

Для обеспечения своевременной сдачи проекта и выявления отклонений применяются следующие механизмы:
1. **Ежедневный асинхронный статус (Standup):** Участники команды кратко фиксируют в рабочем чате статус по схеме: *Что сделано? Что планируется? Есть ли блокеры?*
2. **Мониторинг Kanban-доски в YouGile:** Кристина (PM) ежедневно отслеживает движение карточек по колонкам (`Backlog` ➔ `In Progress` ➔ `Review` ➔ `Done`).
3. **Обязательное Code Review:** Ни один коммит не попадает в главную ветку без проверки Леной (TL) через Pull Request на GitHub.
4. **Мониторинг логов и Smoke-тестирование:** Проверка доступности бэкенда через эндпоинт `GET https://maks.my/codehog/health` (возвращает `200 OK`) и регулярный просмотр логов сервера на предмет ошибок.
